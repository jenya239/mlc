# Диспетчеризация методов без наследования

Вызов `x.method(...)` — узел `ExprMethod(Shared<Expr>, string, [Shared<Expr>], Span)` в `compiler/frontend/ast.mlc`. Сейчас `script_vm/lower/lower_diagnostics.mlc` помечает его кодом `unsupported_method`. Код лоуэра этим шагом не менялся.

## Решение

Это статическая диспетчеризация по типу записи, известному на этапе лоуэринга, не динамическая.

Таблицы виртуальных методов нет. Во время исполнения выбирать реализацию не из чего: индекс прототипа известен до запуска. Вызов — прямой CALL top-level функции, тот же путь, что `prepare_call_block` в `script_vm/lower/lower_call.mlc` и `lower_known_call` в `script_vm/lower/lower_expression.mlc`.

Резолв на этапе лоуэринга: пара (имя типа записи получателя, имя метода) → одна top-level функция. Имя функции — склейка `type_name + "_" + method_name`, как `parse_extend_method` в `compiler/frontend/parser/decls.mlc` (`docs/agent/notes/methods_frontend_survey.md`). Получатель занимает первый аргумент CALL, параметр `self`. Явные аргументы вызова идут следом, в порядке источника.

Тип записи берётся из типа выражения-получателя, уже известного лоуэру. Если это не запись с таким методом, отказ именной и на этапе лоуэринга, не поиск метода в значении на куче.

## Наследования записей нет

`docs/MLC.md`, принцип 5: наследования нет. Вместо иерархии классов — трейты, `extend` и композиция. `docs/LANGUAGE_DESIGN.md`: нет классов и нет наследования; `extend` — единственный способ добавить методы к типу; трейты не абстрактные классы. У записи нет базового типа, от которого метод мог бы прийти. Одна пара (тип записи, имя метода) имеет не больше одной реализации, поэтому динамическая диспетчеризация не нужна.

Срез без generics: имя типа — голое имя записи, не параметр типа.
