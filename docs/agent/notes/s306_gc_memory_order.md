# Шаг 306 — порядок сборки мусора и байтовый предел

Инкрементальная сборка мусора — это SVGUI-11, после нарезки SVGUI-07…10 (шаги 339–360). В фазе 2 (шаги 323–338) её нет. `heap.write_barrier_hits` инкрементальным барьером не является (§6.3 документа реализации GUI).

До SVGUI-11 полный сбор на потоке runtime service допустим только вместе с жёстким пределом на вызов. Предел временный, для фаз 2 и 3 до отдельного среза SVGUI-11. Это не бюджет бенчмарка шага 301 и не production-профиль фазы 8.

Числа, которые читает шаг 326:

| Предел | Число | Откуда |
|---|---|---|
| Проходов mark-sweep на один вызов хоста | 1 | `heap_in_place_collect` уже делает один mark, один sweep и один compact. Второй вызов в том же host call запрещён. |
| Живые байты элементов | 8192 | `initial_gc_threshold()` в `script_vm/executor_gc.mlc` равен 1024, `value_byte_size()` равен 8. 1024 × 8 = 8192. |
| Инструкций на вызов, если этот сбор запускается | 1024 | Та же константа 1024, как потолок работы, не как число объектов. `instruction_limit == 0` означает «без предела» (`run_limits` по умолчанию) и для этого потока запрещён. |

Живые байты — сумма `element_count` живых слотов, умноженная на 8. `heap_limit_objects` считает объекты и этот предел не заменяет: один массив — один объект и много ячеек `element_arena`. Байт строки в арене хранится как `ValueInt32`, не как один байт файла.

Если после единственного прохода живые байты всё ещё больше 8192, вызов завершается ошибкой лимита кучи. Новый проход не начинается.

Шаг 325 только фиксирует отсутствие живого instance и эти числа не реализует. Шаг 326, если вызывает полный сбор, держит один проход, 8192 байт и 1024 инструкции.
