# MLC: C++-first язык с избирательно переносимыми вычислениями

**Статус:** архитектурный RFC / основополагающее техническое задание для исследовательских агентов. **Не** утверждённый план реализации.  
**Дата:** 2026-10-21  
**Место в репозитории:** `docs/MLC_CPP_FIRST_PORTABLE_COMPUTE_RFC.md` (предложение переноса в `docs/architecture/` не выполнено).  
**Исходный проект:** https://github.com/jenya239/mlc  
**Контекст:** предыдущий проектный документ `mlc_glsl_plan.md` («GLSL-бэкенд для mlc»), 2026-10-21.  
**Приоритет:** исследовать и сохранить архитектуру языка; не запускать реализацию GLSL только на основании этого RFC.

> **Главный инвариант:** MLC остаётся выразительным, практически совместимым с экосистемой C++ языком, который транслируется в идиоматичный C++20. Дополнительные среды исполнения поддерживаются через **избирательную переносимость фрагментов программы**. Ограничения GPU, VM и других таргетов не должны сужать семантику и возможности обычного MLC-кода.

6. Приводить ссылки на конкретные пути, символы, commit SHA, команды тестов и результаты. Не выдавать эскизы MLC-синтаксиса за компилируемый код.

## 1. Миссия MLC и порядок приоритетов

### 1.1. Главная цель

MLC — **языковой слой над C++**, а не замена платформы C++ и не очередная независимая VM-first экосистема. Его ценность состоит в том, что программа пишется на удобном языке, но получает практический доступ к C++20: компиляторам, системным API, заголовкам, библиотекам, инструментам, шаблонам, памяти и низкоуровневым механизмам там, где это позволяет явно определённый интерфейс MLC ↔ C++.

**Доступ ко всей экосистеме C++ — целевое свойство, но его нельзя объявлять уже полностью реализованным.** Требуется отдельная проверка фактического покрытия: `extern`, импорт `.hpp`, namespaces, overload sets, templates, value/reference/pointer semantics, lifetime, ABI, linking и диагностики. Наличие C++-бэкенда само по себе не гарантирует прозрачного импорта произвольного C++ API.

### 1.2. Дополнительная цель

Разрешить отдельным функциям, модулям или вычислительным графам MLC выполняться в специализированных средах:

- GPU: поначалу GLSL/OpenGL, затем — только при доказанной необходимости — SPIR-V/Vulkan и другие платформы;
- VM: **выборочно**, после определения, какая именно VM и какие гарантии нужны;
- прочие вычислительные таргеты (CPU SIMD, WASM, специализированные DSP и т. п.) — возможные направления, не обещания.

Здесь переносится **алгоритм или вычислительный фрагмент**, а не вся программа, весь C++ runtime или вся экосистема C++.

### 1.3. Иерархия архитектурных приоритетов

1. Корректность и выразительность основного MLC → C++20 пути.
2. Сохранение и постепенное расширение C++ interop, без искусственных ограничений из GPU/VM.
3. Самохостинг и доступный Ruby bootstrap; существующие регрессионные контракты.
4. Предсказуемая семантика языка: типы, владение, порядок вычисления, ошибки, диагностики.
5. Явная и проверяемая избирательная переносимость.
6. Оптимизация и расширение числа таргетов.

Если выбор улучшает п. 5–6, но портит п. 1–4, он отвергается по умолчанию.

## 2. Архитектурные инварианты (не обсуждаются без отдельного ADR)

**I-01 — C++-first.** Нормальная программа MLC должна продолжать компилироваться в C++20. GPU/VM — специальные проекции, а не ограничения всего исходного языка.

**I-02 — Экосистема C++.** `extern` и любые существующие/будущие инструменты C++ header interop — самостоятельное первоклассное направление. Нельзя заменять их изолированным GPU SDK или собственным замкнутым runtime.

**I-03 — Избирательность.** Переносимость определяется на уровне конкретных функций, специализаций и графов вызовов; она не требует объявления всего модуля «GPU-языком» и не запрещает иметь рядом обычный C++-код.

**I-04 — Аддитивность.** Добавление нового таргета меняет доступные проверки/преобразования, но не переопределяет привычный смысл исходного C++-пути.

**I-05 — Явные границы.** Код не должен случайно уходить на GPU или исполняться в VM. Компиляция, размещение ресурсов, запуск, синхронизация и копирование данных управляются явно определёнными интерфейсами.

**I-06 — Проверяемая переносимость.** Компилятор не должен обещать поддержку таргета по синтаксису одной функции, игнорируя её зависимости, конкретную инстанциацию generic, внешние вызовы, ресурсы и ограничения устройства.

**I-07 — Не только `pure`.** GPU-kernel может записывать в изображения/буферы, пользоваться атомиками и barrier. Переносимость и чистота — разные свойства. Эффекты нужны как минимум для контроля допустимых операций и порядка исполнения.

**I-08 — Интероперабельность без магии.** Внешний C++ вызов по умолчанию непрозрачен для GPU/VM. Совместимость устанавливается только через доказанный portable body, явный target-specific intrinsic или альтернативную реализацию с проверяемым контрактом.

**I-09 — Отдельность ABI и сериализации.** C++ ABI, native struct layout, std140/std430, VM value layout и host↔device transfer layout не считаются взаимозаменяемыми. Нужны явные адаптеры и тесты.

**I-10 — Никакого штрафа за неиспользование.** Проект без GPU/VM не должен требовать соответствующих библиотек, драйверов, манифестов, компиляции специальных функций или дополнительных runtime-зависимостей.

**I-11 — Не ухудшать самосборку.** Изменения типов, checker и пайплайна не могут ломать Ruby bootstrap и повторную генерацию C++.

**I-12 — Диагностики от исходника.** Ошибки переносимости и GPU-компиляции должны по возможности указывать место в `.mlc`, цепочку вызовов и требуемую capability; генерация непонятного GLSL — недостаточный результат.

## 3. Неравноправная архитектура таргетов

### 3.1. Концептуальная схема

```text
                           MLC source modules
                                  |
                         Lexer / Parser / AST
                                  |
                         Resolver / Type checker
                                  |
                              SemanticIR
                                  |
             +--------------------+---------------------+
             |                                          |
       PRIMARY PATH                               OPTIONAL PATH
             |                                          |
   C++ semantics/codegen                    Select entry / call graph
   (all host language)                                 |
             |                             Target eligibility + effects
           CppAST                                       |
             |                               Specialization / lowering
             v                                          |
        C++20 source                         [portable lowered subset]
             |                                          |
    C++ headers / linker                     +----------+----------+
    existing C++ ecosystem                   |                     |
                                          GLSL                 other backend
                                            |                 (only if needed)
                                         GPU shader
```

В схеме **нет обязательного общего ComputeIR для всего языка**. Если эксперименты покажут, что несколько дополнительных таргетов реально разделяют операции и оптимизации, допустимо выделить внутренний `PortableIR` **только после** проверки, что он не навязывает ограничения host-коду.

### 3.2. SemanticIR, MIR и VM

- **SemanticIR** сохраняет полную семантику MLC и является основным кандидатом для анализа достижимости, типов и эффекта вызовов.
- **MIR** уже существует, но его фактическую пригодность для f32/u32, SSA/CFG, ABI, структур и portable lowering необходимо проверить по текущему коду. Не утверждать заранее, что весь проект обязан идти через MIR.
- **Script VM и compiler MIR/VM — разные подсистемы.** В репозитории `docs/MLC_SCRIPT_VM.md` прямо различает script-profile VM и `mlcc --run`/MIR VM. Нельзя обещать автоматическую поддержку script VM просто потому, что появился GLSL.
- **CppAST** не заменяется новым универсальным AST. Он продолжает обслуживать основной C++-путь.

### 3.3. Избегать архитектурного переворота

**Запрещённый анти-паттерн:** `MLC → PortableIR → {C++, GPU, VM}` как единственный путь для любого MLC-кода. При таком устройстве переносимое подмножество очень легко начинает определять все допустимые конструкции языка.

**Допустимый компромисс:** для чисто математических или ресурсно-ограниченных функций повторно использовать часть общего lowering и проверки эффектов, но обычные host-функции должны сохранять прямой путь к C++.

## 4. Модель переносимости: не булевый флаг `@gpu`

### 4.1. Capability-based eligibility

Нужна проверка вида:

```text
eligible(function specialization, target profile, reachable dependencies)
    → Supported | Unsupported(reasons[]) | Unknown(reasons[])
```

На решение влияют:

- типы и их представление (скаляры, векторы, records, arrays, pointers, opaque resources);
- операции и встроенные функции;
- эффекты (alloc, I/O, FFI, device read/write, atomics, barriers, nonlocal control flow);
- конкретные инстанциации параметризованных функций;
- граф вызовов и target-specific implementations;
- версия целевого языка, доступные расширения, precision/features устройства;
- стадия GPU (fragment, compute, vertex), включая допустимые intrinsics и control-flow constraints;
- правила layout и передачи значений.

Пример: `f64` не «всегда запрещён на GPU», а может требовать отдельную capability и поддерживаемую версию/устройство. Даже в пределах одной платформы поддержка fragment и compute может различаться.

### 4.2. Три независимых понятия

**А. Фактически пригодна.** Функция автоматически проходит анализ для target profile.

**Б. Обязана быть пригодна.** Разработчик просит компилятор проверить и гарантировать поддержку профиля. В случае ошибки — понятная диагностика.

**В. Является точкой входа.** Функция соответствует контракту запуска shader/kernel; это не то же самое, что «обычная функция доступна на GPU».

Спорный синтаксис намеренно не фиксируется. Кандидаты `@gpu`, `@requires(gpu)`, `@portable(...)`, объявления kernel/stage — предмет UX-исследования. `@gpu module` из прежнего плана может быть **удобным сокращением**, но не должен становиться обязательным способом организации исходников.

### 4.3. Транзитивность и локальность требований

- Проверять весь **достижимый граф вызовов** от выбранной GPU-entrypoint, а не все функции файла.
- Обычная host-функция, вызывающая portable helper, остаётся host-функцией.
- Функция с одним несовместимым `extern` не делает автоматически несовместимым весь модуль.
- Для generic решение зависит от **конкретной инстанциации**; функция может быть portable с `f32`, но не с `std::string` или непрозрачным C++-типом.
- Расширения target profile должны вести к монотонному расширению множества поддерживаемых операций, насколько это возможно; исключения документируются.
- `Unknown` не означает успех: opaque FFI без контракта должен приводить к отказу выбранного переноса или требованию специальной реализации.

### 4.4. Пример только для иллюстрации модели (синтаксис предварительный)

```mlc
// Обычная функция. Её тело может быть вычислимо и на CPU, и на GPU.
fn sphere_sdf(p: Vec3, radius: f32) -> f32 = length(p) - radius

// Host: используются обычные C++ interop и средства MLC.
extern fn native_log(message: string) -> unit = "native_log" from "host.hpp"
fn inspect(p: Vec3) -> f32 = do
  native_log("inspecting point")
  sphere_sdf(p, 1.0)
end

// Здесь намеренно НЕ указан синтаксис запуска kernel:
// entrypoint — отдельный проверяемый контракт платформы.
```

Это иллюстрация **разделения ролей**, а не тестовая программа. `Vec3`/`f32` и их точные имена/поддержка должны быть проверены/спроектированы.

## 5. C++ interop — отдельная, главная программа исследований

До обсуждения переносимых GPU-вычислений агенты обязаны сделать **baseline C++-совместимости**, а не предположить её существование из-за генерации `.cpp`.

### 5.1. Обязательная матрица C++-совместимости

| Сценарий | Что проверить | Критерий |
|---|---|---|
| Обычный C API из `.h` | `extern fn`, линковка | MLC → C++ → вызов системной/сторонней библиотеки |
| C++ namespace и перегрузки | имена/overload resolution | Вызов двух перегруженных функций, корректная диагностика |
| C++ шаблоны | доступ к `template<T>`, явные инстанциации | MLC может вызвать template API без ручной переписи его реализации, либо ограничение явно зафиксировано |
| Типы и классы | `extern type`, opaque/native class | Метод/конструктор/деструктор, правила владения |
| Ссылки, указатели, const | `T&`, `const T&`, `T*`, move | Корректная и документированная семантика жизненного цикла |
| Заголовки и зависимости | `#include`, package/include paths | Воспроизводимая сборка со сторонним C++ проектом |
| `std::vector`, `std::string` и иные STL-типы | маппинг MLC ↔ C++ | Отсутствие случайных копий/аллокаций; явно показаны преобразования |
| ABI/исключения/RAII | ownership, error boundary | Не происходит UB, утечек, невидимых исключений |
| Инкрементальная сборка и диагностики | clang++/линкер/source mapping | Ошибка из внешнего header объяснима на стороне пользователя |
| Native performance | аллокации, копирование, dispatch | Реальный generated C++ и результаты benchmark, а не утверждение «zero cost» |

Матрицу заполнять по факту `PASS / PARTIAL / FAIL / NOT TESTED` с указанием хоста, toolchain, версии библиотеки и логов. **Этот аудит может оказаться важнее GLSL-бэкенда.**

### 5.2. Существующий дизайн импорта заголовков

Отдельно изучить `docs/CPP_PARSER_DESIGN.md` и его реализацию. Уточнить, насколько реально работают:

1. Импорт/анализ заголовка без ручного перечисления сотен `extern` функций.
2. Сохранение/проксирование синтаксиса C++ там, где MLC не обязан его понимать полностью.
3. Классы, методы, шаблоны, макросы, namespaces, typedef/using.
4. Делегирование сложной семантики C++ компилятору без попытки построить второй Clang.
5. IDE-диагностики и навигация к native symbol.

Сравнить минимум три стратегии: **ручные декларации `extern`**, **генерируемые декларации/адаптеры из header (например, с помощью Clang tooling)**, **ограниченный native C++ escape hatch**. Оценить сложность сопровождения и полноту покрытия. Не считать собственный парсер полноценного C++ неизбежной инвестицией.

### 5.3. Переиспользование C++ на GPU

Не обещать автоматическую компиляцию произвольного `.hpp` в GLSL. Разделить три случая:

- **Host only:** библиотека исполняется только в C++; portable код может работать рядом, но не вызывать её внутри GPU-kernel.
- **Portable wrapper:** алгоритм реализован на MLC, использует переносимое ядро и может вызываться также из host C++.
- **Target-specific implementation:** один семантический контракт имеет C++-реализацию через header и отдельную проверенную GPU-реализацию/intrinsic.

Последний случай требует явных правил эквивалентности поведения, выбора реализации, инстанциации generic, тестов и документации пограничной точности. **Одинаковая сигнатура не означает одинаковую семантику.**

## 6. Семантические границы CPU ↔ GPU ↔ VM

### 6.1. Типы

Обычный MLC сохраняет свои `Shared<T>`, COW-коллекции, строки, `Result`, traits, `extern` и другие возможности независимо от GPU-поддержки. Вычислительным таргетам доступны только представимые в них типы/операции.

Исследовать:

- `f32`, `u32`, fixed arrays и векторы как **полноценные типы MLC**, имеющие C++ lowering, а не «GPU-only типы»;
- примитивы, которые можно выразить через библиотеку и C++ interop, прежде чем добавлять новые варианты `Type`;
- совместимость арифметики `VecN` с generic и операторными traits (фактический статус traits нужно проверить);
- record value semantics, `mut`/`inout`, компоненты матриц, swizzle и aliasing;
- sum types и `Option` лишь когда возникнет доказанный сценарий; representation не должен ломать C++-семантику.

**Особый риск:** если GPU-oriented `Vec3` в host C++ имеет layout, отличный от std140/std430, нельзя считать его bytes прямым GPU-параметром. Использовать явный маршаллинг либо специально определённый host-visible GPU-layout type.

### 6.2. Эффекты и ресурсы

Минимально различать:

```text
read/write locals; reads/writes GPU buffers/images;
atomics; synchronization/barriers; dynamic allocation;
blocking/async; host I/O; opaque/native FFI;
nonlocal control flow; recursion; unsupported intrinsics.
```

Не вводить сразу полную академическую effect system, если минимальный статический анализ графа вызовов и явные маркеры решают задачу. Но **не смешивать** pure computational helper и entrypoint с side effects.

`sampler`, `image`, SSBO, UBO и shared workgroup memory — **ресурсы с особыми ограничениями**, а не произвольные C++ объекты. Требуются правила областей видимости, доступа, binding и lifetime; для opaque типов нельзя использовать обычную универсальную модель значений. См. официальную GLSL 4.60 спецификацию.

### 6.3. Порядок исполнения и десугаринг

MLC expression-oriented. Lowering `do`, `if`, `match`, `?`, лямбд и compound expressions должен учитывать:

- порядок оценки аргументов и подвыражений;
- короткое замыкание `&&`/`||`;
- условные эффекты и точки раннего выхода;
- `mut`/aliasing и `inout`;
- сохранение исключаемых побочных действий при `@static` специализации;
- барьеры, которые нельзя произвольно переносить между ветками/итерациями.

Сам факт, что GLSL-код компилируется, **не доказывает эквивалентность** исходнику MLC.

### 6.4. Численная семантика

Отдельно специфицировать:

- rounding и поведение `f32`/`f64`;
- преобразования signed/unsigned, overflow, shifts;
- `NaN`, `Inf`, signed zero, `mod`/`%`, divide by zero;
- `fma`, reassociation, fast-math, `sin`/`cos` и прочие transcendental builtins;
- precision qualifiers / расширения / драйверы;
- целевые допуски CPU/GPU сравнения.

**Нельзя требовать универсальной битовой идентичности GPU с C++** или одинаковой скорости на всех драйверах. Нужны зафиксированные численные режимы и тестовые tolerances по классам операций.

### 6.5. Dispatch и host/runtime интерфейс

Компиляция вычислительного kernel и его исполнение — разные операции:

```text
select kernel/specialization → validate capabilities → compile/build artifact
→ allocate/bind resources → dispatch → synchronize → consume result
```

Нельзя скрывать копирование памяти или синхронный readback в обычном вызове функции без отдельного явного контракта. Обычный вызов portable helper из C++ по умолчанию означает **CPU-исполнение**, а не миграцию на GPU. Будущие высокоуровневые API могут выбрать устройство, но выбор, стоимость трансфера и условия fallback должны быть наблюдаемы.

## 7. Архитектурные альтернативы, которые агент обязан сравнить

| Вариант | Суть | Сильная сторона | Риск |
|---|---|---|---|
| A — Прямой SemanticIR → GLSL | Дополнительный минимальный lowering | Самый короткий путь к эксперименту | Дублирование, трудная масштабируемость |
| B — SemanticIR → PortableIR → GLSL | Специальный нормализованный IR только для выбранных функций | Общие проверки/оптимизации | Досрочный дизайн IR, «второй язык» |
| C — Доработать существующий MIR | Использовать/расширить существующий CFG для GPU | Снижение числа промежуточных представлений | Можно перегрузить MIR несовместимыми целями |
| D — C++ → внешний shader/toolchain | Использовать существующие компиляторы/DSL для GPU | Меньше собственного кодогена | Потеря MLC source diagnostics/семантики, ограничения инструмента |
| E — Тонкая MLC-обёртка над Slang/другим shader language | Встраивать GPU-ядра отдельно, сохраняя C++-host | Минимальный риск host | Не единый исходник алгоритма |

Для каждого варианта обязательны: диаграмма, необходимые изменения checker, влияние на C++-путь и Ruby bootstrap, сумма новых семантических правил, тестируемость, пользовательский API, обратимость решения.

**Никакой вариант не предрешён.** Для первого прототипа A естественен, но это гипотеза, а не мандат. B разрешать только при предъявлении конкретного повторно используемого lowering/анализа для двух независимых потребителей.

### Что изучить в качестве технических ориентиров

Не как обязательные зависимости, а для сравнения семантики и UX:

- Slang: несколько shader target'ов, generics и specialization;
- ISPC: SPMD-вычисления и C/C++ integration;
- Taichi: portable kernels, runtime/backend separation;
- SYCL и CUDA C++: близость host/device к C++, атрибуты и ограничения;
- Halide: разделение алгоритма и schedule;
- Clang tooling/libclang: импорт C++ деклараций.

Цель обзора — выявить **проверяемые архитектурные уроки**, а не составить список библиотек и не копировать их концепции без адаптации к MLC.

## 8. Отношение к прежнему GLSL-плану

`mlc_glsl_plan.md` — **входной технический материал и перечень гипотез**, но больше не является основным архитектурным планом. Агенты должны присвоить его пунктам категории `KEEP`, `MODIFY`, `DEFER`, `REJECT`, `VERIFY`.

| Исходная идея | Предварительный статус | Основание |
|---|---|---|
| Отдельный GLSL backend | KEEP/VERIFY | Практичный эксперимент, но таргет вторичен |
| Lowering из SemanticIR | KEEP/VERIFY | По описанию отвечает структуре текущего компилятора |
| `f32`, `u32`, `VecN` | KEEP | Полезные host-типы, не только для GPU |
| `@gpu` на всех функциях | MODIFY | Нужен reachability + eligibility, аннотация — требование, не дубль типов |
| `@gpu module` | DEFER | Можно сделать синтаксическим сокращением позднее |
| `@fragment`, `@compute` | KEEP/VERIFY | Контракт запуска необходим; синтаксис не утверждён |
| GlslAST и emitter | KEEP/VERIFY | Простой отдельный codegen возможен |
| Manifest/resource reflection | KEEP (минимум) | Полезный контракт host ↔ GPU |
| Полные sum types и упаковка вариантов | DEFER | Нет в минимальной потребности, сложный ABI |
| Generic monomorphization | DEFER | Нужна после core slice; зависит от существующего checker |
| Self-tail recursion elimination | DEFER | Специальная оптимизация не обязательна для первого успеха |
| Scene-as-static-data + CT evaluator | DEFER | Отдельная языковая программа с высоким риском scope creep |
| Полный порт Horus | DEFER | Сначала доказать cross-target функцию |
| Сохранять Python/moderngl-хост | KEEP | Хороший внешний потребитель и регрессионный эталон |
| «Не медленнее 5%» | MODIFY | Измерять; считать не порогом успеха языка, а отдельной метрикой |
| «1 ULP / bit-identical» | MODIFY | Нужны численные контракты по операциям/платформам |

**Обнаруженные проблемы исходного плана, требующие проверки:**

1. SSBO c двумя runtime-sized массивами в одном блоке — не соответствует общему правилу GLSL: такой массив может быть только последним членом блока. Нужен другой layout.
2. `Image2D`/sampler нельзя моделировать как обычные value types без ограничений GLSL opaque resources.
3. Предлагаемая замена `mut`-параметра на `inout` требует отдельной семантики aliasing, side effects и lifetime.
4. Объявленное целевое разнообразие GLSL 330/430/450 требует разных capabilities; нельзя делать их одним бинарным «GPU support».
5. CPU↔GPU сравнение «один исходник» не равно универсальному `1 ULP`/pixel identity.
6. GLSL integration не должна становиться причиной замены полного SemanticIR или ухудшения CppAST.

GLSL-контракты сверять с [Khronos GLSL 4.60](https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.60.html), а не только с успешным запуском на llvmpipe.

## 9. Поэтапная исследовательская программа (решения по воротам)

### R0. Зафиксировать baseline и границы (без изменений компилятора)

**Задача:** картографировать существующий pipeline, interop и гарантии.

Шаги:

1. Зафиксировать SHA, ветку, toolchain, версии Ruby, Clang, Mesa, тестов.
2. Проследить минимальную программу через AST, checker, SemanticIR, CppAST, generated C++.
3. Найти рабочие примеры native `extern`, классов/headers, linking и generic.
4. Проверить реализацию/планы C++ header parser и отличить код от design-only.
5. Составить карту MIR и script VM без смешения этих подсистем.
6. Выполнить существующие гейты, записать исходное состояние.

**Gate R0:** воспроизводимый audit с evidences и матрица C++-interop. Нет доказательств — статус `UNKNOWN`, не `PASS`.

### R1. Семантическая feasibility (сперва дизайн)

**Задача:** определить минимальный переносимый профиль `numeric-core-v0`:

- scalar arithmetic: `i32`, `u32`, `f32`, `bool` (при подтверждении вводимых типов);
- `Vec2/3/4` (или проверенный существующий C++-vector interop);
- вызовы простых функций, `if`, `for`/`while`, локальные мутации;
- records только с совместимым layout;
- внешние native вызовы **запрещены внутри переносимого графа**, пока нет verified mapping;
- никакой динамической памяти, GC/COW, closures с окружением, рекурсии и full generic specialization в первом срезе;
- shader resources и stage entrypoint **за границей математического ядра**.

Выходы: компактная compatibility matrix, требуемые ошибки checker, формальное описание порядка вычисления и допусков float. Оценить три варианта A/B/C до выбора IR.

**Gate R1:** можно точно указать, почему произвольная функция доступна или недоступна для таргета, не меняя host-язык.

### R2. Малый end-to-end эксперимент (только отдельный утверждённый TRACK)

**Одна MLC-функция → два исполнения:**

1. Параметрический SDF/поле или другой численный helper.
2. Host-ветка компилируется MLC → C++ и вызывается внутри программы, использующей **реальный C++ header**.
3. GPU-ветка компилируется тем же MLC source → GLSL; небольшой compute/fragment probe вызывает ту же функцию.
4. Сравнить результаты по чёткой численной метрике; неверные операции вызывают понятную диагностику.
5. Не требовать sum types, @static-evaluator, большого shader host, рендеринга Horus и переноса существующей VM.

**Gate R2:** сохранился весь host use case; cross-target функция фактически одна и та же; не добавились обязательные зависимости в C++-only проекты.

### R3. Проверка выразительности на двух независимых случаях

Рекомендуемые кейсы:

- **SDF:** математика, ветвления, векторы, точность, вызовы;
- **Gray–Scott или другой stencil compute:** массивы, явные ресурсы, записи, workgroup, синхронизация и transfer.

Не начинать с полного Horus; использовать его после двух малых кейсов как нагрузочный интеграционный тест. C++-сторона должна быть не игрушечной: использовать нативные библиотеки/headers хотя бы на host boundary.

**Gate R3:** добавление второго кейса не потребовало дублировать математический исходник, сломать host интероп или внедрить универсальный IR всему языку.

### R4. Решение о платформенной архитектуре

После R3 ответить:

- Нужен ли PortableIR, либо прямой GLSL lowering достаточен?
- Достаточны ли локальные capabilities или нужна отдельная effect system?
- Действительно ли нужен compile-time specialization уже сейчас?
- Каков минимальный публичный kernel/resource/dispatch API?
- Что даёт переносимость по сравнению с обычным C++ + отдельным GLSL?
- Где самое узкое место: compiler complexity, C++-interop, API usability, runtime transfer, shader performance?

Только после этого утверждать roadmap полной GPU-интеграции и выбора новых таргетов.

## 10. Тесты и измерения, обязательные для решений

### 10.1. Основной компилятор (регрессия)

Агент обязан следовать **текущим** командам `AGENTS.md` и `docs/agent/DEVELOPMENT.md`; ориентир на дату RFC:

```bash
bash scripts/dev_gate_fast.sh
compiler/tests/build_tests.sh
bash scripts/regression_gate.sh
MLCC_FORCE_RUBY=1 compiler/build.sh  # в предписанных repo случаях
```

При изменениях compiler и закрытии трека также проверять двухпроходный self-host diff, описанный в `README.md` и `docs/agent/DEVELOPMENT.md`. **Ни одна команда из этого раздела не заявлена выполненной при подготовке данного RFC.**

### 10.2. GPU и корректность

- Static positive/negative tests на каждую capability и тип несовместимости с местом `.mlc`.
- Парсер/типчекер не должен нарушать host C++ генерацию.
- `glslangValidator` + фактическая компиляция GLSL драйвером; версии GLSL фиксируются.
- Пробные вычисления с проверкой `abs`/`relative`/ULP/PSNR **по смыслу теста**, не единый порог для всего.
- Отдельные edge cases: `NaN`, `Inf`, нулевые делители, индексация, aliasing, порядок выражений.
- Host↔device binding/layout через проверенные offsets и размеры, а не предположение о C++ struct layout.
- Прогон на нескольких драйверах только при доступности; отсутствие покрытия явно фиксировать.

### 10.3. Качество интеграции

Для каждого эксперимента указать:

- сколько MLC-строк дублируется между CPU/GPU;
- нужен ли bridge C++/MLC/GLSL, сколько в нём рукописных мест;
- насколько хорошо ошибки shader/kernel маппятся в исходник;
- какой дополнительный build latency и размер output;
- сколько обязательных GPU-зависимостей попало в host-only сборку (**целевое значение: ноль**);
- точные CPU/GPU benchmark-условия, без сравнения разных физических машин как равных;
- как быстро агент может внести небольшое изменение математической функции и проверить оба исполнения.

### 10.4. Критерии провала / условия остановки

Остановить расширение GPU-функций и вернуться к архитектуре, если:

1. Требуется отказаться от важных C++-возможностей в host-коде или менять их семантику.
2. Таргетный checker начинает ограничивать функции, не участвующие в переносимом графе.
3. Поддержка PortableIR становится обязательной для C++-only сборок без доказанной выгоды.
4. Функции дублируются вручную на CPU/GPU настолько, что «один исходник» теряет смысл.
5. Граф вызовов с opaque FFI ошибочно признаётся переносимым.
6. Не удаётся сохранить bootstrap/self-host и существующие regression gates.
7. Сложность решения превосходит пользу по сравнению с внешним shader toolchain; критерии сравнения должны быть заранее сформулированы, а не придуманы после эксперимента.


## 12. Разделение ролей агентам

### Architect (исследователь архитектуры)

Строит pipeline map, варианты A/B/C, проверяет I-01..I-12, описывает степень обратимости, **не меняет компилятор**.

### C++ Interop Auditor

Проверяет реальные headers, native types, templates, linking, lifetime и latency. Сдаёт исполнимую матрицу; не принимает за реализацию содержимое design-only документов.

### Semantic Auditor

Изучает checker/IR, call graph, monomorphization, effects, `f32`/`VecN`, короткое замыкание и native extern calls. Формулирует `eligible(...)` и негативные тесты. Не проектирует компилятор GLSL заранее.

### GPU Researcher

Сверяет GLSL spec и ресурсную модель; исследует minimal SDF/compute slice, возможности конкретного OpenGL профиля, численную эквивалентность. Не требует переноса всего Horus.

### Critic / Reviewer

Ищет любую скрытую уступку host C++, необоснованное усложнение IR, ложную переносимость и притворную численную идентичность. Сдаёт письменный вердикт `GO / NARROW / STOP` с проверяемыми причинами.

### Driver (только после утверждения TRACK)

Реализует **один узкий шаг**, соблюдает существующий `CONTINUITY.md`/`DEVELOPMENT.md`, запускает установленные гейты и приводит логи. Никакого «переписать весь GLSL-бэкенд» одним треком.

Роли — логические; это не инструкция запускать оркестратор и не изменение установленной в репозитории системы ролей.

## 13. Вопросы, которые исследование обязано разрешить

### Стратегические

1. Насколько полно **сейчас**, а не в плане, mlc подключает C++ headers/templates и какие пробелы наиболее болезненны?
2. Можно ли реализовать переносимый численный core без добавления чужеродного GPU-диалекта языка?
3. Не сильнее ли продуктовый выигрыш от исправления C++ header import, чем от нового GPU backend?
4. Как обеспечить «один исходник для CPU/GPU» без обещания одинакового поведения всех библиотек C++?

### Семантические

5. Должна ли переносимость выводиться полностью автоматически, либо нужны требования и явные trusted mappings?
6. Как задавать target profiles (OpenGL 330/430/460, этап shader, capabilities, device extensions)?
7. Можно ли сделать target-specific implementations со **строго одинаковым контрактом**, а не только сигнатурой?
8. Что происходит с generic instantiation и overload resolution в рамках portable subgraph?
9. Какие минимальные эффекты компилятор обязан отслеживать для корректного переносимого lowering?
10. Что считать CPU reference при возможных различиях float, vector ABI и intrinsics?

### Архитектурные

11. Требуется ли новый PortableIR **по фактическим операциям**, а не из эстетических соображений?
12. Можно ли расширять существующий MIR, не загрязняя его ресурсами GLSL и device-specific semantics?
13. Как взаимодействуют host CppAST, Shader AST, package system, manifest, build/link pipeline?
14. Как увязать target-specific specialization с существующим self-host/bootstrap и Ruby parity?
15. Как не перепутать portable numeric kernels с самостоятельной script VM, которая имеет другую модель исполнения?

### Практические

16. Как выглядит минимальный удобный MLC API для shader entry, ресурсов и dispatch без скрытых дорогих операций?
17. Стоит ли CPU-эталон генерировать как C++, а не пытаться сразу выполнять его в VM?
18. Можно ли отлаживать одну переносимую функцию на CPU обычными C++ tools и затем переносить её на GPU без переписывания?
19. Какие два независимых кейса действительно валидируют архитектуру, а не только удачно подобранный shader?
20. Какие наблюдаемые преимущества даёт решение по сравнению с MLC + отдельный GLSL/Slang проектом?

## 14. Формат итогового аналитического заключения агента

Заключение должно иметь именно такую структуру:

```text
1. Snapshot: SHA / branch / тестовая среда
2. Confirmed facts: путь:символ/строка, команда, результат
3. Current C++ interop matrix: PASS/PARTIAL/FAIL/NOT TESTED
4. Semantic constraints: types, effects, external calls, target features
5. Alternative architectures: A/B/C/D/E with trade-offs
6. Proposed minimal user API (concept vs compilable syntax clearly labeled)
7. One-source CPU/GPU proof of concept: exact gate
8. Host-only regression and bootstrap risks
9. Proposed ADRs and unresolved owner decisions
10. Final recommendation: GO / NARROW / STOP, reasons
11. Smallest next TRACK: dependencies, files, tests, stop conditions
```

**Критерий качества отчёта:** другой агент, не участвовавший в анализе, способен проверить ключевые факты и результаты без догадок и без доверия автору.

**Критерий хорошего архитектурного решения:** оно одновременно делает C++-разработку на MLC удобнее или не хуже, а переносимость отдельных вычислений — реальной, проверяемой и полезной.

## 16. Короткий мандат следующему агенту

> Проведи аудит текущего MLC как C++-first языка и исследуй архитектуру избирательной переносимости вычислений в GLSL/GPU и потенциально другие таргеты. Не меняй код на первом этапе. Сначала подтверди реальное состояние C++ interop и пайплайнов по SHA, затем предложите минимум три архитектурных варианта, формальную границу допустимого переносимого графа вызовов и крошечный end-to-end эксперимент «один MLC helper, C++ host с настоящим C++ header, GLSL compute/fragment». Не ограничивай обычный MLC возможностями GPU, не вводи обязательный PortableIR, не смешивай compiler MIR с script VM, не принимай планы за реализованные возможности. Верни доказательства, матрицы, решение GO/NARROW/STOP и самый маленький безопасный TRACK согласно правилам репозитория.
