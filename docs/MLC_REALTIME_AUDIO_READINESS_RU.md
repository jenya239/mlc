# MLC для аудиоядра: диагностика и план доработок

**Дата:** 2026-10-22. **Статус:** техническое задание для будущего диагностического трека; реализация не начата.

**Цель:** установить, какие части аудиоядра для паттернового музыкального редактора можно надёжно писать на MLC, выявить конкретные препятствия в языке, компиляторе, runtime и FFI и устранить их минимальными проверяемыми изменениями.

**Контекст:** интерфейс на textui; собственные инструменты и эффекты; поддержка всех сторонних плагинов не требуется. Предмет документа — готовность самого MLC, а не разработка клона FL Studio.

## 0. Как агенту исполнять этот документ

1. Прочитать актуальные [CONTINUITY](agent/CONTINUITY.md), [DEVELOPMENT](agent/DEVELOPMENT.md), [spec index](specs/index.md) и активный TRACK. Этот документ не меняет приоритет существующих очередей.
2. Запрос пользователя на данном этапе — подготовить документ. Наличие предложенных этапов ниже не означает, что они выполнены или что следует автоматически начинать реализацию. При последующем поручении исполнять документ двигаться от диагностики к минимальным исправлениям без повторных запросов на рутинные действия в пределах поручения.
3. Перед диагностикой записать HEAD, dirty diff, версию и происхождение mlcc, Ruby bootstrap, C++ compiler и flags. Не приписывать поведение исходников устаревшему бинарнику. Чужой WIP не откатывать, не включать в свой коммит.
4. Читать только относящиеся к проверке документы и код. Не возобновлять `misc/editor/` и не использовать его старые perf harness как доказательство готовности textui.
5. Каждое утверждение маркировать: **код**, **эксперимент**, **документ**, **гипотеза**, **предложение**, **не проверено**. Ссылки на код без запуска подтверждают устройство реализации, но не время выполнения.
6. Одна гипотеза и один измеряемый срез на Green. Сначала Red или воспроизводимый baseline, затем исправление и повтор того же сценария. Никакого общего «улучшения архитектуры» без привязки к дефекту.
7. Эскизы новых API не представлять как существующий синтаксис. Сначала проверять точный вызов через оба компилятора и запуск бинарника.

**Результат первого прохода:** отчёт о возможностях и пробелах, работающие минимальные пробы, численные baseline, список обязательных исправлений и решение о допустимой границе MLC/C++. Никаких заранее выставленных статусов «готов к real-time».

## 1. Границы задачи

Включено:

- MLC → C++20, Ruby bootstrap и self-host parity для используемого подмножества;
- численные типы, циклы, передача структур, состояние DSP, буферы и время жизни;
- callback из нативной библиотеки в скомпилированный MLC;
- атомики, ограниченные очереди, публикация состояния и освобождение ресурсов;
- диагностики и инструментирование опасных операций;
- воспроизводимые headless и device-тесты с минимальной нагрузкой textui.

Не включено в первый цикл:

- VST/AU/CLAP host, совместимость проектов FL Studio, коллекция инструментов;
- полноценный piano roll, timeline, запись с диска и time-stretch;
- новый backend компилятора, общий borrow checker, глобальная смена модели COW;
- GPU DSP, Script VM в аудиоколбэке, многопоточный DSP scheduler;
- обещание hard real-time на обычной настольной ОС.

MLC должен оставаться пригодным для обычных программ. Ограничения аудиопотока локальны. Новый контейнер или диагностика не должны молча менять value semantics существующего `Array`.

## 2. Модель будущей нагрузки

Три области исполнения:

| Область | Разрешённая работа | Запрещённая зависимость |
|---|---|---|
| Управление: UI и проект | Коллекции, undo, построение нового плана, проверки, подготовка команд | Аудиопоток не должен ждать завершения этой работы |
| Фоновые workers | Декодирование, загрузка, освобождение retired-ресурсов, запись результатов | Нельзя обращаться к активному mutable DSP-состоянию без протокола |
| Аудиоколбэк | Ограниченный набор событий, DSP по готовым буферам, публикация компактных счётчиков | Heap, блокировки, I/O, ожидание workers, UI/GL, логирование строками |

Обобщённый путь данных: события с позицией в отсчётах → голоса инструментов → эффекты каналов → суммирование → выходной буфер.

Первый движок имеет фиксированную маршрутизацию. Аудиопоток владеет mutable состоянием голосов, фаз, огибающих и фильтров. UI передаёт команды и подготовленные immutable данные, а не изменяет эти поля напрямую.

**Контракт ядра, псевдоописание:** обработать заранее проверенные входные/выходные представления буферов и отсортированный список событий заданной длины, обновить состояние на месте, вернуть компактный статус. Память для всего перечисленного уже существует.

Обработка того же блока должна вызываться и из device callback, и из offline harness. Нельзя делать быстрый игрушечный benchmark, обходящий настоящий путь вызовов, dispatch или управления состоянием.

## 4. Обязательные свойства горячего пути

После подготовки и до выхода из callback, включая деструкторы временных объектов:

- ноль выделений, перевыделений и освобождений heap-памяти в проверенном пути;
- ноль mutex/condition-variable waits, sleep, join, файловых и консольных операций;
- отсутствие скрытой инициализации static/TLS с блокировками при первом вызове;
- отсутствие выхода исключения через ABI; ожидаемые ошибки возвращаются статусом;
- ограниченная работа: заранее заданы максимум голосов, событий и команд на блок;
- нет обхода всего проекта, сортировки всей песни, бесконечного retry/CAS-loop;
- стабильные адреса активных буферов и недоступность их освобождения другим потоком;
- никакого изменения общих глобальных настроек floating point без восстановления;
- корректный выход при нулевом/необычном размере блока и смене sample rate согласно явному lifecycle.

Среднее время, отсутствие GC и нативная компиляция сами по себе не подтверждают ни один из этих пунктов. Lock-free не равно wait-free; lock-free структура с неограниченным retry не удовлетворяет требованию ограниченной работы.

## 5. Диагностическая матрица языка и codegen

Для каждой строки: маленький исходник → Ruby-путь → self-host-путь → C++ → executable → функциональный результат → allocation/timing probe. Где сборка не проходит, сохранить диагностику и минимальный reproducer, не обходить проблему незаметным переносом алгоритма в C++.

| ID | Проверка | Обязательные варианты / доказательства |
|---|---|---|
| L01 | Численные типы | Реальное покрытие `f32`, `f64`, знаковых/беззнаковых целых; width/layout и conversions; упоминание `f32` в codegen не доказывает полный путь |
| L02 | Циклы DSP | Индексные циклы, вложенные каналы/кадры, отсутствие per-sample allocation; сравнение оптимизированного машинного кода при необходимости |
| L03 | Передача состояния | Малый record, вложенный record, массив в record, параметры/return/ref-mut: где реально возникает copy/move/detach |
| L04 | Запись в буфер | Чтение, запись, представление поддиапазона, alignment, bounds; совпадение адреса буфера до/после вызова |
| L05 | Generic и dispatch | Мономорфизация и concrete call path; tagged union/match, функция, замыкание с/без захвата; стоимость и heap у каждого |
| L06 | Математика | sin/exp и выбранные операции, linking, точность, денормалы, NaN/Inf; первый вызов отдельно от steady-state |
| L07 | Владение | Последний refcount decrement, уничтожение временных значений, unwind/error paths; память освобождается вне callback |
| L08 | Оптимизация | Фактические flags, inlining, aliasing, vectorization report; запрет выводить «SIMD работает» из названия типа |
| L09 | Ошибки | Bounds failure, недопустимый handle, переполнение, пустой event list; отсутствие исключения/abort в нормальном callback |
| L10 | Parity | Одинаковая семантика критических проб через Ruby и self-host; frozen output только там, где он устойчив |

Отдельно проверить: вызывается ли функция обработки один раз на блок, а не extern на каждый отсчёт; может ли C++ compiler видеть тело цикла и оптимизировать его. Нельзя ставить `restrict`/noalias без доказанной семантики непересечения.

## 6. Буферы и память: сначала контракт, затем API

Целевые свойства возможного нового буфера:

- тип элемента и количество элементов определены явно; `f32` предпочтителен как кандидат, но его поддержку нужно доказать; `f64` допустим для первого корректного среза;
- storage выделяется/инициализируется в prepare, адрес стабилен до teardown;
- callback получает non-owning view: адрес, длина, при необходимости stride;
- mutable view имеет одного writer; immutable sample data разделяется только на чтение;
- view не владеет освобождением и не может пережить storage; способ обеспечения контракта описан явно;
- subview/bounds/переполнение расчёта размера проверяются; «всё unsafe» не считается решением;
- inplace и out-of-place processing имеют отдельные правила aliasing;
- buffer exhaustion возвращает предсказуемый статус вне горячего пути; запрещён fallback на heap;
- очистка выполняется за O(размер блока), освобождение — после остановки/подтверждения.

Сравнить по эксперименту: существующие FFI/raw-pointer средства; специализированный runtime buffer; узкая аддитивная возможность языка. Выбирать минимальный вариант, позволяющий написать сам DSP на MLC.

Не менять обычный Array на «уникальный всегда» и не считать `reserve` защитой от detach. Region исследовать отдельно: upstream allocation, capacity, reset, alignment, lifetime вложенных ресурсов. На первом срезе предпочтительнее фиксированное хранилище, чем аллокатор внутри callback.

## 7. Callback ABI и lifecycle

Диагностика должна пройти весь путь native driver/stub → compiled MLC → заполнение native output buffer.

Проверить:

1. Calling convention, linkage, типы параметров и возврата, размер frame count, packing/layout, nullable input.
2. Function pointer и user-data: можно ли зарегистрировать MLC-функцию; если нужен trampoline, перечислить его точные обязанности и ABI-причину.
3. Callback вызывается чужим потоком: инициализация TLS/runtime, thread-affinity и отсутствие зависимости от scheduler MLC.
4. Контекст живёт до последнего callback; start/stop/restart и неудачный start не оставляют висячие указатели.
5. Stop/join и освобождение выполняются управляющим потоком. Никакого teardown из самого callback.
6. Размер блока может отличаться от запрошенного. Для превышения prepared maximum выбрать bounded chunking либо fail-safe тишину/статус; не делать resize.
7. Ошибка внутри DSP не пересекает C ABI исключением; статус/тишина и сигнал управляющему потоку. Это не оправдывает blanket catch, скрывающий дефекты.

Минимальный native stub сначала вызывает callback синхронно и с worker thread, проверяет буфер sentinel-значениями и многократный lifecycle. Затем подключается реальное устройство. Успех stub не равен успешному device-тесту.

## 8. Команды, публикация и reclamation

Первый кандидат — фиксированное SPSC-кольцо: один producer управления и один consumer аудио. Несколько UI/worker источников сводятся на управляющем потоке; не расширять незаметно контракт до MPSC.

Обязательные проверки очереди:

- capacity, wrap-around счётчиков, full/empty, порядок, отсутствие дубликатов и частично опубликованного payload;
- trivially destructible payload или доказанный bounded lifecycle; никаких строк, owning Array или Shared с последним release в consumer;
- реально lock-free атомики на поддерживаемом target, включая разрядность и alignment;
- publication happens-before чтения payload; возможное ослабление `seq_cst` допускается только с объяснением и тестами;
- максимум команд за блок; producer не может заставить callback бесконечно догонять очередь;
- overflow policy по классу команд. Изменение громкости можно объединить; note-off/stop нельзя молча терять и оставлять зависшие голоса;
- отрицательные тесты и длительный concurrent stress; ThreadSanitizer отдельно от timing runs.

Публикация подготовленного плана должна описывать полный цикл: prepare → publish → audio accepts at block boundary → acknowledge old generation → reclaim on control/worker.

Один atomic pointer не решает use-after-free. Простой double buffer тоже не безопасен, если producer перезаписывает ещё читаемый слот. Нужны поколения, подтверждение и ограниченный запас слотов. При исчерпании слотов control откладывает/объединяет обновления; audio не ждёт.

План маршрутизации, immutable sample storage и mutable DSP-state — разные сущности. При смене плана определить, какие голоса/хвосты продолжают жить, где хранится их состояние и когда старые семплы перестают использоваться. Не копировать большой state внутри callback ради «снимка».

## 9. Численная и временная корректность

- Источник времени — целочисленная позиция в аудиоотсчётах. Musical ticks и BPM преобразуются с сохранением дробного остатка либо другой доказанной схемой без накопления дрейфа.
- Событие имеет offset внутри блока. Проверить offset 0, N−1 и N: событие на правой границе относится к следующему блоку. Установить порядок одновременных note-off/note-on/parameter events.
- Проверить loop wrap, seek, stop, смену BPM и повторяемость при разных размерах блока.
- Громкость/частота сглаживаются по явно заданному правилу; тестировать переходы и отсутствие разрыва там, где обещана непрерывность.
- Для sampler: границы семпла, интерполяция, stereo/mono, окончание голоса и детерминированное voice stealing.
- Для stateful DSP: impulse response, continuity между блоками, тишина после затухания, bounded поведение при NaN/Inf согласно выбранной политике.
- Denormals: отдельный затухающий сигнал. FTZ/DAZ, если применяются, документируются для каждой архитектуры и восстанавливаются; глобальный fast-math не является исправлением по умолчанию.
- Численные допуски задаются до Green: абсолютная/относительная ошибка, проверка пиков и накопления. Не требовать одинаковых байтов float между разными toolchain без отдельного основания.

## 10. Harness и воспроизводимые измерения

Новые имена ниже — предложения, файлов и результатов пока нет. Размещать пробы в отдельном каталоге, например `misc/audio_probe/`, scripts — в `scripts/`, отчёты — в `docs/agent/reports/audio_readiness/`. Не смешивать диагностический код с продуктовым textui или корнем compiler.

### 10.1. Контроль инструментария

В начале создать намеренно плохие пробы: allocation, free, mutex, выход за буфер, двойное освобождение и потеря события. Проверить, что соответствующий детектор ловит каждую. Не запускать заведомо UB в обычном процессе вместе с остальными тестами.

Allocation guard должен учитывать new/delete, malloc/free/realloc и relevant aligned/custom allocators, а не только один wrapper. Счётчики thread-local/preallocated; сохранение отчёта вне callback. Указать охват и известные слепые зоны. Проверять release деструкторов и первый реальный callback после prepare, а не только прогретый цикл.

Instrumentation и sanitizers меняют время. Разделить functional/sanitized, allocation-audit и optimized-timing сборки. Запретить printf, файловую запись, динамические histogram containers и stack trace allocation внутри измеряемого callback.

| P02 | Осциллятор + огибающая, затем sampler | Изменяемое состояние без скрытого heap |

| P06 | Публикация/retirement под нагрузкой | Lifetime, overflow, отсутствие callback free |
| P07 | Реальный backend + нагрузка textui | Deadline и underrun в условиях конкуренции |

P01–P04 имеют эквивалентный простой C++ reference с теми же алгоритмами, типами, flags, состоянием и входными данными. Reference не подменяет MLC-реализацию. Защитить вычисления от удаления optimizer через проверяемый результат, а не volatile в каждом отсчёте.

### 10.3. Матрица и метрики

Стартовая матрица: 44,1/48 кГц; блоки 64/128/256/512; основной профиль 48 кГц, 128 frames, stereo. Стартовые числа — требования к эксперименту, не измеренные возможности MLC. Дополнительно проверить неожиданные размеры 1/17/127 и изменение размера между вызовами.

Для каждого прогона сохранить:

- commit, dirty patch hash, compiler binary hash, flags, CPU/OS/kernel, backend/device, power mode, affinity/priority и фактические настройки устройства;
- seed, workload, число голосов/событий, длительность, warm-up, повторы;
- callback duration p50/p95/p99/p99.9/max, число deadline misses, driver underruns;
- allocations/frees, queue high-water, overflow/coalesced/rejected events, retired backlog;
- DSP correctness/error, NaN/Inf, lifecycle failures;
- отдельно CPU execution cost и callback scheduling/wakeup delay, если backend позволяет их измерять; не выдавать одно за другое.

Offline tight loop показывает throughput, а не соблюдение реальных deadline. Device runs требуют реального backend; отсутствие устройства — `not run`, не pass.

Для P07: baseline без UI; idle textui; scroll/hover/resize; worker load и burst команд. Сохранить сценарий и одновременно считать затраты UI отдельно. Не использовать старый native editor. Изменения textui подчиняются собственным file-size/hover/perf gates.

### 10.4. Начальные критерии приёмки

**Безусловные:** корректный результат, ноль выявленных callback allocations/frees/locks, ноль sanitizer defects, отсутствие потерь критических команд и use-after-free. Бounded overload работает по контракту.

**Предлагаемый performance target**, фиксируемый до оптимизаций на выбранной reference-машине: P04 с 64 голосами sampler+огибающая+gain/pan и P03 с одним master-фильтром; 48 кГц/128 frames. Период блока = 128/48000 ≈ 2,667 мс. p99.9 времени callback ≤ 50% периода; observed max < периода; ноль observed deadline misses/driver underruns в трёх device-прогонах по 10 минут, включая P07. Точные DSP fixtures фиксируются в baseline.

Эти пороги — проектный запас, а не физическая гарантия ОС. Failure требует выяснить, виноваты kernel/codegen, scheduling, backend или нагрузка; нельзя просто увеличить буфер или снизить voices и сохранить прежний статус pass. Другие машины получают отдельный профиль.

MLC/C++ ratio — диагностический сигнал, не универсальный SLA. Для P01–P03 устойчивое замедление >20% при одинаковой семантике требует исследования codegen; если noise сопоставим с разницей, сначала исправить измерение. Корректность важнее выигрыша ratio.

## 11. Как выбирать доработку

Для каждого подтверждённого gap представить: reproducer, причина, затронутый слой, альтернативы, минимальное исправление, изменение семантики, compatibility risk, Red и ожидаемый показатель Green.

Приоритет решений:

1. Корректно использовать уже существующее средство, если оно проходит проверки.
2. Добавить узкий runtime/FFI primitive с ясным lifetime-контрактом.
3. Исправить конкретный дефект checker/codegen/parity.
4. Добавить аддитивную возможность языка только если первые варианты дают неприемлемую семантику или измеренную стоимость.

Возможные результаты исследования, не заранее обязательный backlog:

| Gap | Кандидат на исправление | Что не делать автоматически |
|---|---|---|
| COW в sample loop | Уникальное storage + non-owning view | Менять семантику всех Array |
| Нет callback export | Минимальная поддержка ABI/trampoline | Переносить весь DSP в C++ |
| Blocking Channel | Специализированное фиксированное SPSC | Переписывать общий concurrency runtime |
| Последний release в audio | Retirement и bounded ownership handoff | Считать atomic shared_ptr решением real-time |
| Неполный f32/convert | Сквозное покрытие точного пробела | Вводить SIMD/JIT до scalar baseline |
| Hidden allocation | Устранить конкретный lowering/capture/temporary | Объявлять все замыкания запрещёнными в языке |
| Нет проверок RT-контракта | Сначала runtime guards + явный call graph audit | Обещать доказанный WCET по одной аннотации |

Если позднее предлагается аннотация real-time/noalloc, определить её точный смысл и транзитивность: generic специализации, indirect calls, extern, деструкторы, unknown callee. `thread_safe` недостаточно; «не аллоцирует» тоже не значит «не блокирует». Не добавлять синтаксис до отдельного решения по семантике.

## 12. Этапы исполнения и выходные артефакты

Все этапы ниже имеют статус **proposed**. Один этап может потребовать нескольких узких Red/Green шагов. Их нельзя закрывать по наличию документа.

| Этап | Работа | Выход / критерий перехода |
|---|---|---|
| A0 | Инвентаризация toolchain и L01–L10 | `BASELINE.md`: verified/failed/unknown, команды, исходники и codegen |
| A1 | Инструментарий и P00/P01 | Детекторы ловят намеренные нарушения; C++ reference и MLC результаты воспроизводимы |
| A2 | Буферы и состояние | P01–P03 без callback heap; lifetime/bounds/aliasing проверены |
| A3 | Native callback lifecycle | Stub с foreign thread, start/stop/error/variable block; ABI доказан |
| A4 | Очередь и retirement | P05/P06, overflow semantics, stress + sanitizers; bounded work |
| A5 | Численная корректность и codegen | P02–P04, block-size invariance, timing и сравнение C++ |
| A6 | Реальный backend и textui stress | P07; разделение DSP cost и scheduling; честный pass/fail/not-run |
| A7 | Итоговый аудит | `READINESS.md`: поддерживаемый профиль, ограничения, необходимые следующие изменения |

Изменения самого MLC вставляются узкими шагами после выявившего их Red, а не пакетом в конце. Для каждого шага указывать конкретные файлы, слой, зависимость и regression gate. В соответствии с DEVELOPMENT не смешивать `compiler/**` и `lib/mlc/**` в одном шаге.

В итоговом отчёте четыре допустимых решения:

- **MLC пригоден для проверенного профиля:** ядро написано на MLC, нативная часть ограничена перечисленными ABI/platform обязанностями; gates прошли.
- **Пригоден с ограничениями:** перечислены доступные буферы/типы/операции/targets и исключённые пути.
- **Требует доработки:** воспроизводимые blockers и минимальный следующий Red/Green.
- **Недостаточно данных:** например, нет device run или compiler binary не соответствует source.

Фраза «готово для DAW вообще» недопустима: сертифицируется конкретный путь и нагрузка, а не весь язык.

## 13. Проверки репозитория

Для документации без изменения compiler/runtime — ссылки, Markdown, согласованность статусов, session lint; не выдавать это за тестирование аудио.

Для реализации действуют актуальные AGENTS/DEVELOPMENT. Минимально:

- `bash scripts/dev_gate_fast.sh` для Driver-изменений компилятора;
- `compiler/tests/build_tests.sh` и self-host diff по DEVELOPMENT при `compiler/**`;
- `bundle exec rake test_mlc` при `lib/mlc/**`;
- `MLCC_FORCE_RUBY=1 compiler/build.sh` перед закрытием изменений checker/frontend/codegen или Ruby parser/semantic gen;
- `scripts/regression_gate.sh` с exit 0 перед закрытием compiler-трека; требования CONTINUITY для `lib/mlc/**` также сохраняются;
- релевантные runtime tests и новые functional/allocation/concurrency gates;
- при изменениях textui: hard max 400 строк, `scripts/run_textui_file_size.rb`; для paint/submit/hit/frame-loop обязательный `bash scripts/run_textui_hover_bench.sh`, бюджет не повышать; общий `scripts/run_text_gl_perf_corpus.rb` по области изменений.

Команды self-host брать из DEVELOPMENT, не заменять проверкой `--check-only`. Docs-only создание данного задания не требует холодной сборки и не закрывает ни один implementation track.

## 14. Формат отчёта агента и условия остановки

Каждая находка содержит:

- ID, статус доказательности, commit и dirty state;
- минимальный исходник и точную команду воспроизведения;
- expected/actual, generated C++/runtime symbol и причинную связь;
- для perf: одинаковый harness до/после, сырые результаты, количество повторов и разброс;
- исправление либо аргументированное решение «изменения не нужны»;
- regression/parity результаты и оставшиеся unknown.

Остановить расширение решения и сузить шаг, если исчезла воспроизводимость, метрика не меняется, эффект объясняется сменой flags/нагрузки или исправление требует незаявленной смены семантики. Соблюдать правило репозитория о трёх неудачных verify. Не скрывать отсутствие hardware и не превращать неуспешный performance gate в pass изменением порога.

Первый практический deliverable — достоверный ответ на вопрос: **может ли небольшая MLC-функция с изменяемым состоянием обработать реальный аудиоблок без heap/locks, правильно и с измеренным запасом времени?** Если нет, следующий шаг — минимальная причина этого «нет», а не строительство музыкального приложения.

## 15. Внешние технические ориентиры

Эти источники объясняют требования, но не доказывают состояние MLC. При реализации проверить актуальные версии API.

- [PortAudio: callback restrictions](https://portaudio.com/docs/v19-doxydocs/writing_a_callback.html): недопустимость непредсказуемых операций в callback.
- [Image-Line: audio settings](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/envsettings_audio.htm): аудиопоток, буферы, underruns, генераторы и микшер.
- [Image-Line: multicore processing](https://support.image-line.com/action/knowledgebase?ans=476): зависимости между аудиоцепочками ограничивают параллелизм.
- [FL native SDK](https://forum.image-line.com/viewtopic.php?t=12092): интерфейс нативных плагинов, не исходники и не спецификация внутреннего планировщика FL Studio.

Наше разделение потоков, очереди, retirement и предложенные gates — проектные решения для MLC. Не приписывать их внутренней реализации FL Studio без публичного подтверждения.
